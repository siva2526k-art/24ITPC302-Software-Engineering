Question 2 2 Marks | K2 | Unit 1
Differentiate between Verification and Validation in the V-Model.
Model Answer:

• Verification (Left Wing): Static evaluation of work products (reviews, inspections) without code execution to answer: "Are we building the product right?"
• Validation (Right Wing): Dynamic execution of compiled software (Unit, Integration, System, Acceptance testing) to answer: "Are we building the right product?"

Question 3 2 Marks | K2 | Unit 2
List four essential quality characteristics of a good Software Requirements Specification (SRS) under IEEE 830.
Model Answer:

1. Unambiguous: Exactly one interpretation exists for every requirement statement.
2. Complete: Covers all functional, performance, design constraints, and responses to invalid inputs.
3. Consistent: No internal contradictions between requirements.
4. Verifiable: A cost-effective, objective testing procedure can prove compliance.

Question 4 2 Marks | K2 | Unit 2
Define a Petri Net formally and state the transition firing rule.
Model Answer:

A Petri Net is a 5-tuple \(\mathbf{PN = (P, T, F, W, M_0)}\) where \(P\) is Places, \(T\) is Transitions, \(F\) is Flow arcs, \(W\) is Arc weights, and \(M_0\) is Initial marking.
Firing Rule: Transition \(t\) is enabled iff \(\forall p \in I(t), M(p) \ge W(p, t)\). Upon firing, it consumes \(W(p, t)\) tokens from each input place and deposits \(W(t, p')\) tokens into each output place.

Question 5 2 Marks | K2 | Unit 3
Distinguish between Cohesion and Coupling. State the most desirable level for each.
Model Answer:

• Cohesion: Measure of internal functional strength of elements within a module. Most Desirable: Functional Cohesion (Highest).
• Coupling: Measure of interdependence between software modules. Most Desirable: Data Coupling / Uncoupled (Lowest).
Golden Rule: Maximize Cohesion, Minimize Coupling!

Question 6 (a) 13 Marks | K3 | Unit 1
(i) Explain Barry Boehm's Spiral Model of software development with a neat diagram. Describe activities in each of the four quadrants and explain why it is referred to as "risk-driven". [8M]
(ii) Compare and contrast the Waterfall Model with the Spiral Model across 5 project parameters. [5M]
Detailed Model Answer:
Part (i): Boehm's Spiral Model & The 4 Quadrants [8 Marks]

Barry Boehm (1988) designed the Spiral Model as an evolutionary, risk-driven lifecycle model coupling prototyping with Waterfall controls.

QUADRANT II (Risk Assessment) | QUADRANT I (Objectives & Constraints) - Perform thorough risk analysis | - Identify iteration objectives - Build simulations, prototypes, benchmarks | - Establish alternative design approaches ---------------------------------------------+--------------------------------------------- QUADRANT III (Development) | QUADRANT IV (Planning & Review) - Code and verify software artifacts | - Client evaluates deliverables - Unit, integration, and system tests | - Plan next phase / spiral turn

• Why Risk-Driven: At every spiral cycle, effort is guided by the risk associated with that step. If Quadrant II reveals an insurmountable technical risk, development stops immediately, preventing massive financial waste.

Part (ii): Waterfall vs Spiral Comparison Matrix [5 Marks]
ParameterClassical WaterfallBoehm's Spiral Model
Lifecycle ModelLinear sequential, rigid forward stages.Evolutionary, iterative spiral cycles.
Risk ManagementImplicit; no formal risk assessment phase.Explicit, mandatory risk analysis in Quadrant II.
Requirement ChangesInflexible; demands frozen specs upfront.Highly adaptive; accommodates evolving user needs.
Working SoftwareAvailable very late (Construction phase).Early prototypes delivered in early spiral turns.
Best Suited ForStable, well-understood systems (compilers).High-risk, mission-critical enterprise systems.

Question 6 (b) 13 Marks | K3 | Unit 1
(i) What is Extreme Programming (XP)? Describe the 4 core values and illustrate the XP development lifecycle. [7M]
(ii) Detail the mechanisms, working principles, and engineering advantages of: (1) Pair Programming, and (2) Test-Driven Development (TDD). [6M]
Detailed Model Answer:
Part (i): XP Values & Development Lifecycle [7 Marks]

• 4 Values: Communication (open verbal dialogue), Simplicity (build only for today's needs), Feedback (continuous testing and client reviews), Courage (fearless refactoring).
• Lifecycle: User Stories (written on index cards) \(\to\) Release Planning (commitments) \(\to\) Spike Solutions (risk prototypes) \(\to\) Iteration Planning \(\to\) TDD Unit Test \(\to\) Pair Programming \(\to\) Continuous Integration (daily builds) \(\to\) Customer Acceptance Test \(\to\) Production Release.

Part (ii): Pair Programming & Test-Driven Development [6 Marks]

• Pair Programming: Two engineers work on a single workstation. The Driver controls the keyboard and implements code; the Navigator reviews logic, checks corner cases, and plans ahead. Roles switch frequently. Benefits: 15–20% defect reduction, continuous peer review, knowledge dissemination, zero single points of failure.
• Test-Driven Development (TDD): Developers write automated unit tests before writing production code (Red-Green-Refactor cycle). Code is written solely to make failing tests pass. Benefits: Guarantees 100% test coverage, modular decoupled code, complete confidence during refactoring.

Question 7 (b) 13 Marks | K3 | Unit 2
(i) Define a Petri Net formally as a 5-tuple. Explain the transition firing rule and how concurrency and mutual exclusion are modeled. [7M]
(ii) Construct a Petri Net for a Producer-Consumer system with a bounded buffer of size 1. Trace markings across two transitions. [6M]
Detailed Model Answer:
Part (i): Formal 5-Tuple & Concurrency Modeling [7 Marks]

$$\mathbf{PN = (P, T, F, W, M_0)}$$

• \(P\): Places (circles); \(T\): Transitions (bars); \(F\): Flow arcs; \(W\): Arc weights; \(M_0\): Initial marking.
• Enabling Condition: Transition \(t\) is enabled iff \(\forall p \in I(t), M(p) \ge W(p, t)\).
• Firing Rule: Consumes \(W(p, t)\) tokens from each input place; deposits \(W(t, p')\) tokens into each output place.
• Concurrency: Two transitions sharing no input places can fire independently in any order or simultaneously.

Part (ii): Producer-Consumer Synchronization Model [6 Marks]

• Places: \(P_1\) (Producer Ready), \(P_2\) (Buffer Empty), \(P_3\) (Buffer Full), \(P_4\) (Consumer Ready).
• Initial Marking: \(M_0 = [P_1: 1, \ P_2: 1, \ P_3: 0, \ P_4: 1]\).
• Step 1 (\(T_1\) fires - Produce & Deposit): Consumes from \(P_1, P_2\); deposits into \(P_1, P_3 \implies M_1 = [1, 0, 1, 1]\).
• Step 2 (\(T_2\) fires - Fetch & Consume): Consumes from \(P_3, P_4\); deposits into \(P_4, P_2 \implies M_2 = [1, 1, 0, 1] = M_0\).

✓ Proof: Mutual exclusion holds; buffer overflow and underflow are mathematically prevented.

Question 8 (a) 14 Marks | K3 | Unit 3
(i) Illustrate Pressman's 4-Level Software Design Pyramid and explain how each level transforms analysis models into design artifacts. [8M]
(ii) Differentiate High-Level Design (HLD) and Low-Level Design (LLD). Explain the Fan-In vs Fan-Out heuristics. [6M]
Detailed Model Answer:
Part (i): The 4-Level Design Pyramid [8 Marks]
/ \ / [4] \ COMPONENT-LEVEL DESIGN (Algorithms, PDL, Decision Tables) /-------\ / [3] \ INTERFACE DESIGN (User GUI, Internal/External APIs) /-----------\ / [2] \ ARCHITECTURAL DESIGN (Subsystems, Connectors, Arch Styles) /---------------\ / [1] \ DATA / CLASS DESIGN (ER Schemas, Data Structures)

1. Data/Class Design (Base): Transforms analysis classes into DB schemas and data structures.
2. Architectural Design: Establishes system skeleton, subsystem relations, and architectural styles.
3. Interface Design: Defines interaction flow between components, external systems, and human users.
4. Component-Level Design (Apex): Converts structural elements into detailed procedural algorithms and pseudocode.

Part (ii): HLD vs LLD & Design Heuristics [6 Marks]

• HLD: System architecture, subsystem boundaries, DB design. Audience: Architects, clients.
• LLD: Detailed method logic, flowcharts, pseudocode. Audience: Developers, testers.
• Fan-Out: Number of directly invoked submodules (\(3 \le \text{Fan-Out} \le 7\)). High fan-out indicates control overload.
• Fan-In: Number of calling parent modules. Maximize Fan-In for maximum reusability.

Question 8 (b) 14 Marks | K3 | Unit 3
(i) Explain four major Software Architectural Styles: Data-Centered, Data-Flow (Pipe-and-Filter), Layered, and Event-Driven. [8M]
(ii) State and explain any six fundamental software design concepts formulated by Pressman, highlighting Cohesion and Coupling hierarchies. [6M]
Detailed Model Answer:
Part (i): Four Architectural Styles [8 Marks]

• Data-Centered (Repository): Central data store accessed by independent clients. High modularity, but central store is a bottleneck.
• Data-Flow (Pipe-and-Filter): Unidirectional data streams (Pipes) transformed by filters. Highly parallelizable, but poor for interactive UI.
• Layered (Call-and-Return): Hierarchical tiers (UI \(\to\) Business Logic \(\to\) Data Access \(\to\) Database). Loose coupling; multi-layer overhead.
• Event-Driven (Pub-Sub): Producers emit events to an Event Broker; subscribers react asynchronously. Highly scalable; hard to trace.

Part (ii): Pressman's Design Concepts & Cohesion/Coupling [6 Marks]

• Key Concepts: Abstraction, Modularity, Information Hiding (Parnas), Refinement (Wirth), Refactoring, Functional Independence.
• Cohesion Hierarchy (Worst \(\to\) Best): Coincidental \(\to\) Logical \(\to\) Temporal \(\to\) Procedural \(\to\) Communicational \(\to\) Sequential \(\to\) Functional (Best).
• Coupling Hierarchy (Worst \(\to\) Best): Content (Worst) \(\to\) Common \(\to\) Control \(\to\) Stamp \(\to\) Data (Best) \(\to\) Uncoupled.
