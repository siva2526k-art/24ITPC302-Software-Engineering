Part (a): 4 Core Values & 12 Principles of Agile Manifesto

Agile prioritizes customer collaboration, team empowerment, and rapid delivery of working software over rigid plans.

1. Individuals and Interactions OVER Processes and Tools 2. Working Software OVER Comprehensive Documentation 3. Customer Collaboration OVER Contract Negotiation 4. Responding to Change OVER Following a Plan

Q2: The Classical Waterfall Model & Phased Progression 13 MARKS
(a) Explain the Classical Waterfall Model with a neat phase diagram. Detail the activities and deliverables of each phase. [8M]
(b) Discuss the major limitations of the Waterfall model. When is it appropriate to use? [5M]
Part (a): Phases & Deliverables

Phase Sequence: Communication \(\to\) Planning \(\to\) Modeling \(\to\) Construction \(\to\) Deployment.

• 1. Communication (Requirements): Gathers functional/non-functional needs. Deliverable: SRS.
• 2. Planning: Scope, WBS, COCOMO cost, and schedule. Deliverable: SPMP.
• 3. Modeling (Analysis & Design): Data structures, architectural style, component logic. Deliverables: HLD & LLD.
• 4. Construction: Source coding and unit/integration testing. Deliverables: Compiled Code & Test Reports.
• 5. Deployment: User installation, training, and ongoing corrective/adaptive maintenance.

Part (b): Limitations & When to Use

• Weaknesses: (1) Late working software (arrives at construction); (2) High risk of late-stage project failure if requirements were flawed; (3) "Blocking states" where teams wait for predecessor sign-offs.
• When to Use: Stable compilers, operating system utilities, or legacy migration where specifications are 100% frozen upfront.

Q3: Extreme Programming (XP) Values, Lifecycle & Core Practices 13 MARKS
(a) Describe the 4 core values of XP and illustrate the XP lifecycle. [7M]
(b) Explain six core practices of XP, focusing on Pair Programming and Test-Driven Development (TDD). [6M]
Part (a): XP Values & Lifecycle

• 4 Values: (1) Communication (verbal over written), (2) Simplicity (code only for today), (3) Feedback (continuous test & customer feedback), (4) Courage (fearless refactoring).
• Lifecycle: User Stories (index cards) \(\to\) Release Plan \(\to\) Spike Solutions (for risks) \(\to\) Iteration Planning \(\to\) TDD Unit Test \(\to\) Pair Programming \(\to\) Continuous Integration \(\to\) Acceptance Test \(\to\) Production Release.

Part (b): Core Practices (Pair Programming & TDD)

• Pair Programming: Two programmers, one computer. Driver types code; Navigator reviews logic, catches syntax flaws, and plans next steps. Switches roles regularly. Reduces defects by 15–20% and eliminates single-point-of-failure knowledge.
• Test-Driven Development (TDD): Automated unit test written before production code (Red-Green-Refactor). Guarantees 100% test coverage and clean modular design.
• Other Practices: Continuous Integration (multiple daily commits), Small Releases (2-3 weeks), Simple Design (YAGNI), On-site customer.

Q4: Boehm's Spiral Model & Risk-Driven Lifecycle 13 MARKS
(a) Draw and explain Barry Boehm's Spiral Model. Detail activities in each of the four quadrants. [8M]
(b) Why is it termed "risk-driven"? State its advantages and disadvantages. [5M]
Part (a): The Four Quadrants

• Quadrant I (Objective Setting): Identify iteration goals, alternative technical designs, and operating constraints.
• Quadrant II (Risk Assessment & Reduction): Rigorous risk analysis; evaluate alternatives using prototyping, simulation, and benchmarking.
• Quadrant III (Engineering & Development): Implement and verify software artifact (early spirals = architectural prototypes; later = production software).
• Quadrant IV (Planning & Review): Customer reviews deliverables; decide whether to continue, pivot, or terminate project.

Part (b): Risk-Driven Nature & Trade-Offs

• Why Risk-Driven: Effort spent in each cycle is determined by the severity of the identified risks. If high risk cannot be mitigated in Quadrant II, the project stops immediately.
• Pros: Explicit risk mitigation; accommodates changes; early user visibility via prototypes.
• Cons: Highly dependent on expert risk assessment; high process overhead; costly for small systems.

Q5: The V-Model: Verification, Validation & Defect Prevention 13 MARKS
(a) Illustrate the V-Model. Differentiate Verification and Validation. [7M]
(b) Explain phase correspondence and the Defect Prevention Principle. [6M]
Part (a): Verification vs Validation

• Left Wing (Verification): Requirements \(\to\) System Design \(\to\) Architecture \(\to\) Module Design. Static reviews/inspections without code execution ("Are we building the product right?").
• Right Wing (Validation): Acceptance Testing \(\to\) System Testing \(\to\) Integration Testing \(\to\) Unit Testing. Dynamic testing with code execution ("Are we building the right product?").

Part (b): Phase Correspondence & Defect Prevention

• Requirements \(\Longleftrightarrow\) Acceptance Testing; System Design \(\Longleftrightarrow\) System Testing; Architecture \(\Longleftrightarrow\) Integration Testing; Module Design \(\Longleftrightarrow\) Unit Testing.
• Defect Prevention Principle: Test cases are designed concurrently with specifications. Writing acceptance test cases during Requirements Analysis uncovers ambiguities and missing requirements early, preventing defects from entering the code.

Q6: The Incremental Model: Staged Delivery 13 MARKS
(a) Explain the Incremental Model with a neat block diagram. How does it deliver operational capabilities in stages? [7M]
(b) Compare Incremental with Prototyping and Waterfall across risk and delivery timeline. [6M]
Part (a): Mechanism of Incremental Delivery

Applies linear sequences in a staggered, iterative fashion. Increment 1 implements core, non-negotiable capabilities (e.g. basic word processor). Users put it to immediate operational use. Increment 2 & Successive Increments add features (spell-check, formatting) based on real user feedback. Allows flexible staffing: core team builds Increment 1, specialists added later.

Part (b): Comparison Matrix

• Waterfall: Single monolithic delivery at the end; frozen requirements; high risk.
• Prototyping: Throwaway or evolutionary code; clarifies unclear requirements; low risk.
• Incremental: Staged operational deliveries; core requirements known; medium risk.

Q3: Petri Nets: Formal Definition, Firing Rules & Modeling 13 MARKS
(a) Define a Petri Net as a mathematical 5-tuple. Describe primitives and firing rules. [7M]
(b) Model a Producer-Consumer system with a bounded buffer. Trace state transitions. [6M]
Part (a): Formal 5-Tuple & Firing Rules

$$\mathbf{PN = (P, T, F, W, M_0)}$$

• \(P\): Places (circles); \(T\): Transitions (bars); \(F\): Flow arcs; \(W\): Arc weights; \(M_0\): Initial marking.
• Enabling Condition: Transition \(t\) is enabled iff every input place \(p\) has tokens \(\ge W(p, t)\).
• Firing Rule: Consumes \(W(p, t)\) tokens from input places, deposits \(W(t, p')\) tokens into output places: \[ M_{\text{new}}(p) = M_{\text{old}}(p) - W(p, t) + W(t, p) \]

Part (b): Producer-Consumer Synchronization

• Places: \(P_1\) (Producer Ready), \(P_2\) (Buffer Empty), \(P_3\) (Buffer Full), \(P_4\) (Consumer Ready).
• Initial Marking: \(M_0 = [P_1: 1, \ P_2: 1, \ P_3: 0, \ P_4: 1]\).
• Step 1 (\(T_1\) fires - Produce & Deposit): Consumes from \(P_1, P_2\); deposits into \(P_1, P_3 \implies M_1 = [1, 0, 1, 1]\).
• Step 2 (\(T_2\) fires - Fetch & Consume): Consumes from \(P_3, P_4\); deposits into \(P_4, P_2 \implies M_2 = [1, 1, 0, 1] = M_0\).
✓ Guarantees mutual exclusion and prevents buffer underflow/overflow.

Q4: Functional vs Non-Functional Requirements & FURPS+ 13 MARKS
(a) Distinguish Functional and Non-Functional Requirements. Explain FURPS+. [7M]
(b) Provide quantifiable, testable engineering metrics for NFRs. [6M]
Part (a): FR vs NFR & FURPS+ Framework

• Functional Requirements (FR): What the system does (computations, data manipulation, services). E.g. "Calculate simple interest \(I = P \cdot r \cdot t\)".
• Non-Functional Requirements (NFR): Quality constraints and attributes (how well the system performs).
• FURPS+: Functionality (feature set, security), Usability (aesthetics, human factors), Reliability (failure frequency, MTBF), Performance (speed, TPS, memory), Supportability (maintainability, testability), "+" (design, interface, legal constraints).

Part (b): Quantifiable NFR Metrics

• Performance: Response time \(\le 1.5\)s for 95% of requests under 2000 users; Throughput \(\ge 3500\) TPS.
• Reliability: Availability \(\ge 99.99\%\); Mean Time to Recover (\(MTTR\)) \(\le 30\) seconds.
• Usability: 90% of novice users complete account creation in \(< 3\) minutes without operator assistance.

Q1: The Software Design Process & Pressman's 4-Level Design Pyramid 13 MARKS
(a) Illustrate Pressman's 4-Level Software Design Pyramid and explain how each level transforms analysis models. [7M]
(b) Differentiate HLD and LLD. Explain Fan-In vs Fan-Out heuristics. [6M]
Part (a): The 4-Level Design Pyramid
/ \ / [4] \ COMPONENT-LEVEL DESIGN (Algorithms, PDL, Decision Tables) /-------\ / [3] \ INTERFACE DESIGN (User GUI, Internal/External APIs) /-----------\ / [2] \ ARCHITECTURAL DESIGN (Subsystems, Connectors, Styles) /---------------\ / [1] \ DATA / CLASS DESIGN (ER Schemas, Data Structures)

1. Data/Class Design (Base): Transforms analysis classes into DB schemas and data structures.
2. Architectural Design: Establishes system skeleton, subsystem relations, and architectural styles.
3. Interface Design: Defines interaction flow between components, external systems, and human users.
4. Component-Level Design (Apex): Converts structural elements into detailed procedural algorithms and pseudocode.

Part (b): HLD vs LLD & Design Heuristics

• HLD: System architecture, subsystem boundaries, DB design. Audience: Architects, clients.
• LLD: Detailed method logic, flowcharts, pseudocode. Audience: Developers, testers.
• Fan-Out: Number of directly invoked submodules (\(3 \le \text{Fan-Out} \le 7\)). High fan-out indicates control overload.
• Fan-In: Number of calling parent modules. Maximize Fan-In for maximum reusability.

Q2: Software Architectural Styles & Patterns 13 MARKS
(a) Explain Data-Centered Architecture and Data-Flow (Pipe-and-Filter) Architecture with neat diagrams. [7M]
(b) Explain Layered Architecture and Event-Driven Architecture with trade-offs. [6M]
Part (a): Data-Centered & Data-Flow Styles

• Data-Centered (Repository / Blackboard): Central data store accessed by independent client components. Clients add/modify data. Pro: High modularity. Con: Single point of failure/bottleneck.
• Data-Flow (Pipe-and-Filter): Unidirectional data streams (Pipes) processed by transformation nodes (Filters). Pro: Reusable, parallelizable. Con: Inefficient for interactive systems.

Part (b): Layered & Event-Driven Styles

• Layered (Call-and-Return): Presentation \(\to\) Business Logic \(\to\) Data Access \(\to\) Database. Each layer only talks to adjacent layers. Pro: Clean separation of concerns. Con: Multi-layer performance overhead.
• Event-Driven (Pub-Sub): Producers emit events to an Event Broker; decoupled consumers subscribe. Pro: High scalability, asynchronous. Con: Hard to trace/debug.

Q3: Pressman's 12 Fundamental Software Design Concepts 13 MARKS
Detail the twelve fundamental design concepts. Emphasize Functional Independence (Cohesion vs Coupling). [13M]
The 12 Concepts Explained

1. Abstraction: Data/procedural abstraction ignoring low-level details.
2. Architecture: The overall structural layout and component relationships.
3. Patterns: Proven solutions to recurring problems (Observer, Singleton).
4. Separation of Concerns: Subdividing complex systems into independent parts.
5. Modularity: Decomposing software into separately addressable modules.
6. Information Hiding (Parnas): Restricting access to internal module details.
7. Functional Independence: Single focused task, minimal coupling.
8. Refinement (Wirth): Stepwise top-down decomposition of abstract statements into detail.
9. Aspects: Modularizing cross-cutting concerns (logging, security).
10. Refactoring: Restructuring code without changing external behavior.
11. Object-Oriented Concepts: Inheritance, polymorphism, encapsulation.
12. Design Classes: Entity, Boundary, and Controller implementation types.

COHESION (WORST TO BEST): Coincidental -> Logical -> Temporal -> Procedural -> Communicational -> Sequential -> FUNCTIONAL (BEST) COUPLING (WORST TO BEST): Content (Worst) -> Common -> Control -> Stamp -> DATA (BEST) -> Uncoupled

Q1: Barry Boehm's COCOMO I Model & Worked Numerical 13 MARKS
(a) Explain Basic COCOMO I development modes and formulas. [7M]
(b) Sized at 35 KLOC, calculate Effort, Time, Staff, and Productivity for (i) Organic, and (ii) Embedded modes. [6M]
Part (a): Governing Equations

\[ \mathbf{E = a \cdot (KLOC)^b \text{ [PM]}}, \qquad \mathbf{D = c \cdot (E)^d \text{ [Months]}}, \qquad \mathbf{P = \frac{E}{D} \text{ [Persons]}} \]

• Organic: \(a=2.4, b=1.05, c=2.5, d=0.38\). (Small team, familiar domain).
• Semidetached: \(a=3.0, b=1.12, c=2.5, d=0.35\). (Medium team, mixed experience).
• Embedded: \(a=3.6, b=1.20, c=2.5, d=0.32\). (Tight constraints, flight control).

Part (b): Step-by-Step Numerical Solution (KLOC = 35)

(i) Organic Mode:
• \(E = 2.4 \times (35)^{1.05} = 2.4 \times 41.761 = \mathbf{100.23 \text{ PM}}\)
• \(D = 2.5 \times (100.23)^{0.38} = 2.5 \times 5.764 = \mathbf{14.41 \text{ Months}}\)
• Staff: \(P = 100.23 / 14.41 = \mathbf{6.96 \approx 7 \text{ Persons}}\)
• Productivity: \(35,000 / 100.23 = \mathbf{349.2 \text{ LOC/PM}}\)

(ii) Embedded Mode:
• \(E = 3.6 \times (35)^{1.20} = 3.6 \times 71.026 = \mathbf{255.69 \text{ PM}}\)
• \(D = 2.5 \times (255.69)^{0.32} = 2.5 \times 5.922 = \mathbf{14.81 \text{ Months}}\)
• Staff: \(P = 255.69 / 14.81 = \mathbf{17.26 \approx 18 \text{ Persons}}\)
• Productivity: \(35,000 / 255.69 = \mathbf{136.9 \text{ LOC/PM}}\)

✓ Final Answer: Organic = 100.2 PM (7 Staff) | Embedded = 255.7 PM (18 Staff)
Q2: Earned Value Analysis (EVA) Health Audit & Numerical 13 MARKS
(a) Define PV, EV, AC, CV, SV, CPI, SPI, EAC. State interpretation rules. [7M]
(b) BAC = $150,000, 10 months. Month 5: PV = $75,000, EV = $60,000, AC = $70,000. Compute CV, SV, CPI, SPI, EAC, ETC. [6M]
Part (a): Formulas & Rules

\[ CV = EV - AC, \quad SV = EV - PV, \quad CPI = \frac{EV}{AC}, \quad SPI = \frac{EV}{PV}, \quad EAC = \frac{BAC}{CPI} \]

• \(CV < 0 \implies\) Over Budget (Critical); \(SV < 0 \implies\) Behind Schedule (Critical).
• \(CPI < 1.0 \implies\) Spending efficiency is deficient; \(SPI < 1.0 \implies\) Velocity is slow.

Part (b): Step-by-Step Numerical Calculations

• Cost Variance: \(CV = 60,000 - 70,000 = \mathbf{-\$10,000}\) (Project is \$10,000 OVER budget).
• Schedule Variance: \(SV = 60,000 - 75,000 = \mathbf{-\$15,000}\) (Project is \$15,000 BEHIND schedule).
• Cost Performance Index: \(CPI = 60,000 / 70,000 = \mathbf{0.857}\) (Only \$0.86 value per \$1.00 spent).
• Schedule Performance Index: \(SPI = 60,000 / 75,000 = \mathbf{0.800}\) (Progressing at 80% planned rate).
• Estimate at Completion: \(EAC = 150,000 / 0.8571 = \mathbf{\$175,000}\) (Projected \$25,000 overrun).
• Estimate to Complete: \(ETC = 175,000 - 70,000 = \mathbf{\$105,000}\).

✓ Final Answer: CV = -$10k (Over Budget) | SV = -$15k (Behind Schedule) | CPI = 0.857 | EAC = $175,000
Q3: Risk Strategies, Exposure (RE) & Leverage (RRL) 13 MARKS
(a) Distinguish Reactive vs Proactive risk strategies and classify software risks. [7M]
(b) Define Risk Exposure (RE) and Risk Reduction Leverage (RRL). Solve investment decision problem. [6M]
Part (a): Taxonomies & Strategies

• Reactive ("Firefighting"): Team reacts only after crisis manifests.
• Proactive: Formal identification, assessment, mitigation, and contingency planning before work starts.
• Risk Categories: Project Risks (schedule/budget), Technical Risks (performance/design), Business Risks (market/viability), Known, Predictable, Unpredictable.

Part (b): Formulas & Investment Problem

\[ \mathbf{RE = P \times C}, \qquad \mathbf{RRL = \frac{RE_{\text{before}} - RE_{\text{after}}}{\text{Cost of Action}}} \]

• Defect risk has \(P_1 = 0.25\), impact \(C = \$80,000 \implies RE_{\text{before}} = 0.25 \times 80,000 = \mathbf{\$20,000}\).
• Automated test tool costs \(\$6,000\), reduces probability to \(P_2 = 0.05 \implies RE_{\text{after}} = 0.05 \times 80,000 = \mathbf{\$4,000}\).
• \(RRL = \frac{20,000 - 4,000}{6,000} = \frac{16,000}{6,000} = \mathbf{2.67}\).
✓ Since \(\mathbf{RRL = 2.67 > 1.0}\), purchase is highly justified (returns \$2.67 in risk avoidance per \$1 spent).
