# Part I: Level 1 — Conceptual Understanding

### 1. What is the Waterfall Model in Plain English?
Imagine constructing a 50-story skyscraper. You cannot start framing the 20th floor until the foundation is poured and set in concrete. You cannot install the glass windows until the steel frame is assembled. Each stage must finish completely before the next stage can begin.

The **Waterfall Model** (introduced by Dr. Winston Royce in 1970) applied this civil engineering approach to software. It assumes software development is a strictly sequential series of non-overlapping steps: first you talk to the client and write down every requirement in an exhaustive document; once that document is approved and frozen, architects design the complete blueprints; once blueprints are signed off, programmers write the code; once all code is compiled, testers test the whole system; and finally, the system is shipped to the customer.

### 2. Why Did It Become the Foundation of Software Engineering?
In the 1960s and 1970s, the software industry was suffering from the **"Software Crisis"**: programmers wrote code haphazardly without requirements or design (the "Code-and-Fix" approach), resulting in massive cost overruns, missed deadlines, and unmaintainable spaghetti code. 

The Waterfall Model introduced needed discipline:
- It forced organizations to **think before coding**.
- It established formal **written contracts (SRS, SDD)**.
- It created clear, measurable milestone gates for management.

### 3. The Core Weakness: Software is Not Concrete
While a concrete building's design rarely changes once the foundation is poured, software requirements change constantly:
- As users run a system, they discover new needs they could not envision on paper.
- Business markets, tax laws, and technologies evolve while long Waterfall projects are in progress.
- In a rigid Waterfall project, adapting to these changes requires starting over or incurring massive redesign costs.
